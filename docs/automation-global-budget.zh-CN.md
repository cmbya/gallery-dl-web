# 跨博主每轮新增帖子总限额

- 一轮是一次 `/api/automation/trigger` 接受的完整批次，包含该次选中的所有博主；单博主手动触发也使用相同预算。
- 追新与历史补全分别默认 **20 帖**，网页「订阅管理 → 全局控制」可独立配置（1–1000），也可 `PATCH /api/automation/limits`，例如 `{"refresh":20,"history":10}`。设置持久保存在 automation SQLite，不依赖网页会话，修改从新批次生效。
- 额度以**新增完整成功帖子**计算，不是文件数；轮播帖子多文件仍只算一帖。归档重复与未完成失败不占成功额度；置顶帖子成功也占全局额度。原每博主模式限额继续保留。
- 同模式批次仍有排队/运行项时，重复 trigger 不创建另一批，不让已完成前缀重新排队绕过预算。追新/历史批次仍通过既有 Instagram mutex 串行执行。
- 已发现且进入本次追新范围的帖子，在首次下载前保存本地安全 metadata 待办。到达总限额、扫描限额或中断后，未处理的帖子保留；下一轮先处理本地待办再查看新 feed，新帖不会挤掉旧待办。只保存身份、标题、置顶标记，不保存签名媒体 URL、Cookie 或完整 feed。
- 历史继续使用既有 history_pending + cursor 原子页面队列。每轮博主起点持久轮转；失败的追新待办也轮转，避免失败前缀长期饿死后续帖子。
- SQLite `posts.completed` 和 `batch_posts` 成功账本同事务提交。worker 返回丢失、部分成功后失败、取消、暂停恢复或服务重启，都从账本保留已花费额度，而不是相信 worker 最终返回的 completed=0。重启不自动重跑被中断项，已有排队项继续沿用原批次预算。
- 达限原因是 `global_post_limit`（非风控，不全局暂停）。网页显示批次成功/总限额及各博主本地待办数量。
- **不是网络请求上限**：max_pages、max_posts、request_budget 和 timeout 仍独立有限；不会为了凑满20无限扫描，实际成功可能少于额度。尚未发现的帖子不是已持久发现的待办；每博主追新窗口仍按原设置限定，抓全历史应使用历史补全。
